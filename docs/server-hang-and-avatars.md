# Сервер «жив, но не работает» и роботы вместо овалов

## 1. Почему после первого подключения сервер перестаёт принимать игроков и считать попадания

Симптом из консоли клиента:

```
Connected to wss://sv.x1team.ru/
[X1NetworkManager] Подключились к серверу, ждём от него игровую сцену...
```

…и дальше ничего: клиент висит, сервер в статусе «running».

Это **не падение процесса**, а остановка главного потока Unity. WebSocket-рукопожатие
проходит (его ведёт отдельный поток транспорта), но `SceneMessage` и `CmdFire` разбираются
только в главном потоке (`NetworkServer.OnTransportData` вызывается из `Update`), поэтому
для игроков сервер выглядит мёртвым: новый клиент не попадает в сцену, попадания не
засчитываются, у остальных «замирают» соперники. Процесс при этом жив, поэтому
`systemd Restart=on-failure` не срабатывает.

Найдены и исправлены две причины такого залипания — обе воспроизводятся именно при 2+ игроках:

### 1.1. У headless-сервера не было ограничения FPS (главное)

В Mirror (`Assets/Mirror/Core/NetworkManager.cs`, `ConfigureHeadlessFrameRate`) в этой копии
была вырезана единственная строка:

```csharp
Application.targetFrameRate = sendRate;
```

На выделенном сервере нет vsync, поэтому главный цикл Unity крутится настолько быстро,
насколько успевает CPU — обычно 1000–10000 кадров в секунду. Каждый кадр выполняются
`Update`/`LateUpdate` всей сцены и префаба игрока (таймер раунда с `string.Format` и
перестройкой текста TMP, счётчики, Infima-«motions» с пружинами, снимки `NetworkTransform`),
Mono непрерывно собирает мусор. Один игрок ещё терпимо, на втором ядро упирается в 100 %,
и кадр перестаёт «доходить» до сети.

Исправлено в двух местах:

- строка восстановлена в самом Mirror;
- продублирована переопределением `X1NetworkManager.ConfigureHeadlessFrameRate()`
  (поле `headlessTargetFrameRate`, по умолчанию 60 Гц, и аргумент `-fps 60` для правки
  без пересборки) — чтобы ограничение не потерялось снова при обновлении Mirror;
- `X1ServerBuild` теперь **отказывается собирать сервер**, если ограничение пропало и из
  Mirror, и из `X1NetworkManager`.

### 1.2. До 4000 raycast'ов на один выстрел

`NetworkCombatPlayer.CmdFire` «пропускал» союзников и самого стрелка, сдвигая начало луча на
`hit.distance + 0.05` и повторяя `Physics.Raycast`. Если луч стартовал внутри коллайдера
(камера впритык к стене или к союзнику), `hit.distance` равен 0, сдвиг — 5 см, и цикл делал
до `range / 0.05 = 4000` физических запросов на **один** выстрел, всё на главном потоке.
Два стреляющих игрока — сотни тысяч raycast'ов в секунду.

Теперь один `Physics.RaycastNonAlloc` в переиспользуемый буфер и разбор попаданий по
возрастанию расстояния (сортировка вставками, без аллокаций). Стоимость выстрела постоянна.

### 1.3. Меньше мусора в кадре headless-сервера

На сервере нет UI и рендера, поэтому отключено то, что там только жгло кадр:

- `NetworkRoundManager` — `SetActive` панели и перестройка текста таймера (текст обновляется
  теперь ещё и только при смене секунды);
- `LasertagScoreManager`, `NetworkKillScoreUI` — тексты счёта;
- `ButtonColorSelecter` — курсор и панель выбора команды;
- `ColorChanger.ApplyColor` — не создаёт материал на сервере.

### 1.4. Диагностика подключений

`X1NetworkManager.OnServerAddPlayer` больше не падает `NullReferenceException` при пустом
`playerPrefab`, а пишет понятную причину и отключает соединение. Добавлен `OnServerError` —
ошибки транспорта теперь видны в логе, а не выглядят как «сервер просто перестал работать».

## 2. Роботы вместо вертикальных овалов

Новый компонент `Assets/Scripts/RobotAvatar.cs` добавлен на корень префаба игрока
`Assets/Infima Games/Low Poly Shooter Pack/Prefabs/P_LPSP_FP_CH.prefab`.

- собирает простого робота (голова с визором, корпус-майка, рукава, предплечья, штаны,
  ступни, рюкзак), рост ≈ 1.8 м — как у прежней капсулы;
- майка и рукава красятся в цвет команды из `NetworkCombatPlayer.team`:
  `Red` — красный, `Blue` — синий, команда не выбрана — нейтральный серый;
- старая капсула Infima (тот самый «вертикальный овал») гасится по рендеру, объект остаётся
  активным, чтобы не ломать `ColorChanger`;
- **своему** игроку робот не показывается: камера от первого лица, корпус закрывал бы прицел;
- у робота нет коллайдеров, и он лежит на слое `Ignore Raycast`, поэтому попадания
  по-прежнему считает сервер геометрически (`DistanceToBody`), а не по мешу. Регистрация
  попаданий от визуала не зависит;
- на headless-сервере визуал не строится вообще.

### Как потом подставить перерисованные скины

1. Импортировать модель робота (FBX/префаб) **без `NetworkIdentity` и без `NetworkBehaviour`** —
   это чистый визуал.
2. Внутри неё выделить объекты майки в дочерний объект с именем `Jersey` (имя настраивается
   полем `Jersey Object Name`) — его материалы будут перекрашиваться в цвет команды.
   Если такого объекта нет, скин останется таким, каким нарисован.
3. Положить префаб в поле `Skin Prefab` компонента `RobotAvatar` на префабе игрока.
   Процедурный робот при этом не строится.

Анимацию (бег, приседание) можно добавить на скин позже — `RobotAvatar` только создаёт
визуал как дочерний объект и следит за цветом команды, в анимацию не вмешивается.

## 3. Что делать после мержа

1. Открыть проект в Unity 6000.4.0f1, дождаться компиляции и импорта.
2. `python3 -m unittest discover -s tests -v` — проверки исходников (7 тестов).
3. Пересобрать **и сервер, и клиент WebGL**: изменён префаб игрока (добавлен компонент)
   и логика боя. Не смешивать старый клиент с новым сервером.
   Меню: `Build → X1 → Собрать выделенный сервер (Linux x86_64)`.
4. Остановить старый процесс и запустить новый:

   ```sh
   ./LinuxBuild.x86_64 -batchmode -nographics -scene Lasertag \
     -logFile /var/log/x1server.log
   ```

   В логе должно быть:

   ```
   [X1NetworkManager] Headless-сервер: Application.targetFrameRate = 60 Гц
   [X1NetworkManager] Сервер загрузил сцену '.../Lasertag.unity'. Ожидаем игроков.
   ```

5. Проверить: два клиента, стрельба, попадания идут дольше 10 минут; третий клиент
   заходит без перезапуска сервера.

## 4. Чего в этом изменении нет

- Синхронизация остаётся клиент-авторитетной (клиент двигает себя, сервер рассылает
  остальным) — как договорились, пока оставляем.
- Если сервер всё же упадёт нативно (не залипнет), нужен полный лог от запуска до падения:
  `journalctl -u <юнит>` и `/var/log/x1server.log`, код завершения процесса.
  SIGKILL/137 — это OOM-killer, а не краш Unity.
